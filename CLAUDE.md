# Daphycel

Tienda de refacciones y accesorios de telefonía. Dos aplicaciones web, cada una un único archivo HTML autocontenido.

## Archivos del proyecto

- **`daphycel.html`** — Panel interno del negocio. Requiere login (usuario/contraseña) con 3 roles: `dueno`, `administrador`, `vendedor`, cada uno con permisos distintos. Incluye catálogo, punto de venta (POS) con apertura/cierre de caja, cartera de clientes (crédito/fiado), inventario, panel de estadísticas y gestión de usuarios.
- **`daphycel-cliente.html`** — Tienda pública de cara al cliente final, sin login. Incluye catálogo tipo marketplace (con reseñas y calificación por estrellas), consulta de estado de reparaciones por número de orden, y una sección "Mi cuenta" con búsqueda privada por nombre/número de cliente/orden.

## Stack y convenciones técnicas

- **Vanilla HTML/CSS/JS en el frontend.** Sin framework, sin bundler, sin build step. Cada archivo `.html` es autocontenido: su `<style>` y su `<script>` viven en el mismo archivo. Única dependencia de runtime: el cliente JS de Supabase vía CDN (`@supabase/supabase-js@2`).
- **Backend real: Supabase (Postgres + PostgREST + RPC + Storage).** Desde octubre 2026 la fuente de verdad **ya no es `localStorage`**, es una base de datos Postgres alojada en Supabase, compartida de verdad entre cualquier dispositivo que abra cualquiera de los dos archivos (antes la "fuente única" solo sincronizaba entre pestañas del mismo navegador). Ver `supabase-schema.sql`, `supabase-schema-2.sql`, `supabase-schema-3.sql`, `supabase-schema-4.sql`, `supabase-schema-5.sql`, `supabase-schema-6.sql` y `supabase-schema-7.sql` para el esquema completo (tablas, políticas de RLS, funciones RPC, el bucket de fotos, el número de producto automático, los permisos por rol, los pagos pendientes ligados a reparación y los tickets de reparación compartidos) — hay que correr los siete, en ese orden, en el SQL Editor de un proyecto de Supabase nuevo para poder usar la app desde cero. **`supabase-schema-6.sql` reemplaza la función `create_sale`** (le agrega un parámetro) — si se corre, hay que correrlo ANTES de desplegar la versión de `daphycel.html` que lo usa, porque mientras no exista la función de 11 parámetros, `cobrar()` (el checkout del panel) fallaría para CUALQUIER venta, no solo las de pago pendiente. **`supabase-schema-7.sql`** es de menor riesgo (solo quita un `unique`): si no se corre, el panel sigue funcionando normal para equipos individuales, solo falla el registro de "varios equipos" juntos a partir del segundo.
  - **Fotos de producto** (`supabase-schema-3.sql`, octubre 2026): columna `products.image_url` + bucket público `product-images` en Supabase Storage. Se suben desde el panel → Inventario → pestaña **Fotos** (disponible para cualquier rol, incluida vendedora — a diferencia de Editar/Borrar mercancía, cuyo acceso depende de los permisos configurables descritos abajo). Cada subida genera un archivo nuevo (`sku-timestamp.ext`, sin borrar el anterior del bucket) para evitar problemas de caché del navegador al reemplazar una foto. La tienda pública muestra la foto real si existe; si no, sigue usando el ícono/degradado por categoría (`CAT_PHOTO`/`SUBCAT_PHOTO`) como antes.
  - **Número de producto automático y código de barras** (`supabase-schema-4.sql`, octubre 2026): el SKU dejó de ser un campo de texto libre. En el panel → Inventario → Agregar mercancía, el campo "Número de producto" se autogenera y es de solo lectura: usa el contador atómico `increment_counter('producto')` para producir `DPC-00000001`, `DPC-00000002`, etc. (función `formatNumProducto(n)`), y ese valor pasa a ser el `sku` real en `products`. Aparte, hay un campo "Código de producto" independiente (columna `products.barcode`, nullable) pensado para teclearse solo o llenarse con un lector de código de barras físico (actúa como teclado, no necesita integración JS especial) — es el código de fábrica del producto, no tiene relación con el número de producto interno.
  - **Permisos configurables por rol** (`supabase-schema-5.sql`, octubre 2026, solo en `daphycel.html` — el panel interno, no aplica a la tienda pública): el dueño puede decidir, desde Usuarios → "Configurar permisos", qué puede hacer cada rol (`administrador`/`vendedor`) en cuatro puntos: editar/borrar mercancía, ver el panel de estadísticas, cancelar ventas y registrar abonos de clientes (cartera/fiado). Se guarda como JSON en `settings` bajo la clave `role_permissions` (reutiliza la tabla key/value existente, igual que `notify_email`). La función `defaultRolePermissions()` define el valor por defecto si la fila no existe —administrador con inventario+cancelaciones+abonos, vendedor sin nada, igual al comportamiento fijo que había antes de que existiera esta configuración— y `hasPerm(key)` es la verificación en todo el código. El dueño siempre tiene acceso total y no está sujeto a esta configuración. Dentro de Caja (POS) hay un botón "Panel" al inicio del sub-menú (junto a "Venta") que navega directo a la vista Panel, respetando el mismo permiso.
  - **Editar/eliminar cliente** (octubre 2026): en el detalle de cada cliente (Clientes → clic en una tarjeta) hay botones "Editar" y "Eliminar" justo debajo del nombre, disponibles para **cualquier rol, incluida vendedora** — no están sujetos al sistema de permisos anterior, a propósito. "Registrar abono" sigue en el mismo modal pero sí respeta el permiso `abonos` (así la vendedora puede corregir datos del cliente sin poder tocar su saldo/cartera). Eliminar un cliente con ventas o reparaciones ya registradas falla por la FK de `sales.customer_id`/`repairs.customer_id` — se atrapa ese error (`code 23503`) y se muestra un mensaje claro en vez de dejarlo como error genérico de conexión.
  - **"Paga al entregar equipo"** (`supabase-schema-6.sql`, octubre 2026, solo panel): un 5º método de pago en POS → Venta, junto a Efectivo/Tarjeta/Transferencia/Crédito. Al elegirlo hay que escoger a qué orden de reparación abierta (no entregada) va ligada la venta (`sales.linked_repair_id`); la venta se crea de inmediato (el stock se descuenta igual que cualquier venta) con `method:'entrega'`, que actúa como el propio marcador de "pendiente" — por eso `montoPorMetodo()` ya lo excluye de los totales de corte sin cambios, igual que pasa con `credito`. En Equipos para reparar, si una orden tiene ventas `entrega` sin cobrar y su estatus pasa a "Entregado" (o ya estaba en "Entregado"), aparece un botón "Cobrar pendiente" que abre un modal para elegir el método real (efectivo/tarjeta/transferencia); al confirmar se actualiza cada venta pendiente con ese método **y se reescribe su `ts` a "ahora"** (a propósito: para que el corte de caja del día en que se cobra de verdad sea el que la cuenta, no el día en que se vendió el artículo). `pendingSalesForRepair(repairId)` es la función que filtra esas ventas. **Pendiente de desplegar**: el código ya está en `daphycel.html` pero no se sube a Netlify hasta que `supabase-schema-6.sql` se corra en producción — mientras no exista la función `create_sale` de 11 parámetros, el checkout completo del panel (cualquier método de pago) fallaría.
  - **Eliminar equipo en reparación** (octubre 2026): en Equipos para reparar hay un botón "Eliminar" por fila, visible **solo para el rol `dueno`** (hardcodeado con `currentRole==='dueno'`, no pasa por `rolePermissions` — a propósito, para equipos duplicados o mal capturados). Si el equipo tiene ventas ligadas por `sales.linked_repair_id` (pagos "paga al entregar equipo", cobrados o pendientes) el borrado falla por FK (`code 23503`) y se muestra un mensaje claro en vez del error genérico.
  - **Botón "Vender" en el catálogo interno del panel** (octubre 2026): cada tarjeta de producto en Tienda (la vista de catálogo del panel, no la pública) tiene un botón "Vender" junto a "Ver código" — llama a `addToTicket(sku)` (la misma función que usan el escáner y las tiles de POS) y navega directo a Caja → Venta con el producto ya en el ticket, forzando ese sub-tab activo aunque el usuario hubiera estado antes en Cancelaciones/Equipos. Se deshabilita si `stock<=0`, igual que el patrón ya usado en la tienda pública. No valida stock máximo al agregar (igual que escanear o usar las tiles) — el límite real lo sigue validando `create_sale` en el servidor al cobrar.
  - **Un solo ticket/orden para "varios equipos"** (`supabase-schema-7.sql`, octubre 2026): al registrar equipos con el modo "Varios equipos" (mismo cliente, un llenado con "+ Agregar otro equipo" por cada uno), antes cada equipo recibía su propio `order_no` — el cliente terminaba con un número de orden distinto por cada aparato, aunque los hubiera entregado juntos en una sola visita. Ahora se genera **un solo `order_no` para todo el lote** y se reutiliza en cada `insert` de `repairs`; el `id` interno (`EQ-###`) sigue siendo único por equipo (status, cobro y borrado se siguen manejando por separado, por equipo). Esto requirió quitar el `unique` que tenía `repairs.order_no` (`repairs_order_no_key`) — sin esa migración, registrar un solo equipo sigue funcionando igual que siempre, pero registrar "varios equipos" junto falla a partir del segundo (error de llave duplicada, mostrado como error normal de conexión, sin romper nada ni perder el primero). En `daphycel-cliente.html`, `searchOrder()` cambió de buscar un equipo (`.find`) a buscar todos los que compartan ese número de orden (`.filter`) y los muestra como varias tarjetas bajo la misma búsqueda — así "Copiar link" manda un solo link que ya trae el estado de todos los equipos de esa orden.
  - **Equipos para reparar dividido en tres bloques colapsables** (octubre 2026): "En proceso" (`Recibido`+`En reparación`), "Listos para entrega" y "Entregados" — cada uno es un `<div class="inv-table-wrap card hidden">` con su propia tabla/tbody, que empieza **oculto** (solo se ve el encabezado con el conteo). Hay un buscador por número de orden (`#rqOrderSearchInput`) arriba de los tres bloques: al escribir, cada bloque se filtra a las órdenes que coincidan (resaltadas con `<mark>`) y el bloque se abre solo si encontró algo — al borrar la búsqueda todo vuelve a cerrarse. El encabezado de cada bloque (`.repair-block-toggle`, `data-toggle="proceso|listos|entregados"`) también se puede abrir/cerrar a mano con un clic (estado en `repairBlocksOpen`, independiente de la búsqueda). La lógica de agrupar vive en `REPAIR_GROUPS`/`REPAIR_BLOCK_IDS`, y el render de cada fila se factorizó a `repairRowHTML(r, term)` + `wireRepairRowEvents()` (compartida por los tres `tbody`, ya que las filas se reconstruyen por completo en cada render — no hay riesgo de listeners duplicados).
  - **"Cliente nuevo" / "Cliente existente" al registrar equipos** (octubre 2026): en "Registrar equipo(s)", junto al campo Cliente hay dos radios (`rqCustomerMode`). En **"Cliente nuevo"** (default) se teclea el nombre en `#rqCustomer` y, al guardar, se crea de una vez una cuenta real en `customers` (vía `increment_counter('client')`, igual que "Nueva cuenta" en Clientes) — ya no se intenta adivinar por nombre si el cliente ya existía, como pasaba antes. En **"Cliente existente"** se oculta ese campo y aparece `#rqCustomerSelect` (poblado por `populateRqCustomerSelect()`, mismo patrón que `posCustomerSelect`) para escoger la cuenta exacta, evitando duplicados por error de dedo. El `customerId` resuelto (nuevo o existente) se reutiliza para todos los equipos del lote si es "Varios equipos". Tras guardar, el formulario siempre vuelve a "Cliente nuevo".
  - **Cartera de clientes como lista + balance de reparaciones** (octubre 2026): la vista Clientes dejó de mostrarse como tarjetas en cuadrícula (`.client-card`/`.client-grid`, ya eliminadas) y ahora es una tabla (`table.inv`, mismo patrón que Usuarios/Inventario) con columnas Número, Nombre, Teléfono, Cliente desde, Compras y Saldo — el número de cliente (`C-001`, etc., ya existía internamente vía el contador `client`) ahora es visible y también se puede buscar por él en `#clientSearchInput`. En el detalle del cliente (`openClientModal`), además del historial de compras (que se mantiene sin cambios), hay una sección "Equipos / reparaciones": cuenta cuántos están `Entregado` vs. el resto ("Pendientes", agrupando Recibido/En reparación/Listo para entrega) y lista cada equipo con su folio (`r.order`), estatus y **costo de la reparación** (`r.cost`); si el cliente nunca registró un equipo, muestra "No tuvo reparación" en vez de una lista vacía.
  - **Producto externo al catálogo en POS → Venta** (octubre 2026): botón "Producto externo" junto al escáner, para vender algo que no está en inventario (ej. un artículo de una sola vez). Abre un modal (`#externalProductModal`) para nombre/precio/cantidad; genera una clave temporal `EXT-<timestamp>-<random>` que solo vive en memoria durante ese ticket (`externalItemsInfo`, nunca se persiste) — `findProduct()` revisa ese mapa como respaldo si el sku no está en `products`, así que `renderTicket()`/`ticketTotals()` funcionan sin tocarlos. Al cobrar, esas líneas se mandan a `create_sale` con `sku: null` (igual que los cobros de mano de obra de reparación) para que nunca se intente descontar stock de un producto real. Al cerrar el recibo (`closeReceipt`), si se vendió algo externo, se pregunta uno por uno (`confirm()`) si se quiere registrar en el catálogo — al aceptar, navega a Inventario → Agregar mercancía con el nombre y precio ya prellenados (`#fName`/`#fPrice`), dejando que complete categoría/stock.
  - **IVA opcional + efectivo autollenado en POS → Venta** (octubre 2026): el ticket ya **no aplica el 16% de IVA por default** — hay un checkbox "Aplicar IVA (16%)" (`#posApplyIva`, sin marcar al abrir cada ticket nuevo) que `ticketTotals()` consulta para decidir si suma IVA o no. Además, el campo de efectivo (`#cashInput`) se autollena con el total exacto cada vez que cambia el ticket o se marca/desmarca el IVA — así "Cobrar venta" normalmente no pide teclear nada más. Esto respeta cualquier monto que el cajero haya escrito a mano (ej. para calcular cambio): el autollenado solo pisa el campo si sigue vacío o si todavía tiene el último valor que el propio autollenado puso (`lastAutoFilledCash`), nunca un monto distinto que el cajero haya tecleado.
  - **Imprimir ticket a 80mm** (octubre 2026): el modal de recibo (`#receiptModal`) tiene un botón "Imprimir" junto a "Listo". Arma un ticket con formato de impresora térmica en `#printArea` (oculto en pantalla) y llama a `window.print()`; el CSS de `@media print` oculta todo lo demás (`visibility:hidden` en `body *`, visible solo `#printArea`) y fija `@page{size:80mm auto;margin:0;}` + `width:80mm` en el área — es el patrón estándar para que cualquier impresora térmica de punto de venta lo tome como el ancho de papel correcto, sin depender de configurar la impresora o el diálogo de impresión del navegador.
  - **Costo total de la reparación + enganche/pago completo al registrar el equipo** (octubre 2026): en "Registrar equipo(s)", cada bloque de equipo tiene dos campos opcionales: "Costo total de la reparación" y "Paga ahora / enganche". Si se captura un pago ahora (>0), se crea de inmediato una venta real (`tipo:'reparacion'`, `linked_repair_id` = ese equipo, método elegido en el radio compartido `rqPayMethod`) — por eso ese cobro **ya cuenta en la caja del día**, igual que cualquier otra venta. `repairs.charged` se marca `true` solo si lo pagado ahora cubre el costo total; si no, el equipo queda con un anticipo pendiente. `repairPaidSoFar(repairId)` suma todas las ventas `tipo:'reparacion'` ligadas a ese equipo (sin cancelar) para saber cuánto se ha cobrado en total. En la fila de Equipos para reparar, si hay anticipo sin liquidar se muestra "Anticipo $X de $costo" + botón "Cobrar resto ($restante)"; `openRepairChargeModal()` prellena ese restante (editable) y, al confirmar, `rcConfirmBtn` **nunca sobrescribe el costo total ya fijado** — solo lo hace si `repairs.cost` seguía en 0 (caso de equipos registrados sin fijar costo, el comportamiento de antes de esta función: el primer cobro define el costo y lo marca cobrado). Esos cobros de mano de obra (tanto el de "Cobrar" como el de "pago ahora" al registrar) ahora sí guardan `linked_repair_id` y `customer_id` — antes no se guardaban, lo cual rompía el cálculo de `repairPaidSoFar` y el balance de reparaciones de Clientes si no se corrige ahí también.
  - **Link copiable por reparación** (octubre 2026): el botón "Copiar link" en cada fila de Equipos para reparar genera `daphycel-cliente.html?orden=<order_no>` (ruta relativa al propio origen, así que funciona igual en local y en producción sin URL hardcodeada) y lo copia con `navigator.clipboard.writeText` (si el navegador lo bloquea, cae a un `prompt()` con el link para copiarlo a mano). En `daphycel-cliente.html`, el bloque de init lee `?orden=` de la URL al cargar, salta directo a la vista Reparaciones y dispara `searchOrder()` automáticamente — así el cliente no tiene que teclear su número de orden si recibe el link (ej. por WhatsApp).
  - **Conexión:** `SUPABASE_URL` y `SUPABASE_KEY` (la clave pública `anon`/`publishable`, segura para el navegador) están hardcodeadas al inicio del bloque `PERSISTENCIA` de ambos archivos — es intencional, esa clave está diseñada para ser pública.
  - **Operaciones atómicas vía RPC** (evitan condiciones de carrera reales entre dispositivos, algo que `localStorage` nunca tuvo que resolver): `increment_counter`, `create_sale` (usada tanto por `cobrar()` del panel como por `checkoutOnline()` de la tienda — valida stock servidor y revierte la transacción si no alcanza), `cancel_sale`, `abonar`.
  - **Contraseñas nunca viajan al cliente.** La tabla `users` no tiene política pública de lectura/escritura; todo pasa por funciones `SECURITY DEFINER` (`login_check`, `create_user`, `change_password`, `delete_user`) que jamás devuelven la columna `password`. El resto de las tablas (`products`, `customers`, `sales`, `repairs`, `caja`, `settings`, etc.) sí tienen política pública de lectura/escritura con la clave `anon` — no hay reglas por rol a nivel de base de datos; los roles (`dueno`/`administrador`/`vendedor`) y los permisos configurables descritos arriba son solo gating de UI. Si en algún momento se necesita seguridad real por rol a nivel de datos, hay que migrar a Supabase Auth con RLS por usuario — no está hecho todavía.
  - **Semilla y reseteo:** `window.DaphycelDB.reset()` ya no reinicia nada (antes borraba `localStorage`); ahora solo informa que el catálogo vive en Supabase. Si hace falta reiniciar datos de prueba, usar `seed-supabase.js`/`reset-supabase.js` (en el scratchpad de la sesión que hizo la migración, no están en el repo) o hacerlo directo en el SQL Editor.
- **Dependencias externas** cargadas por CDN únicamente: Google Fonts (Space Grotesk, IBM Plex Sans, IBM Plex Mono), JsBarcode y qrcodejs vía `cdnjs.cloudflare.com`, `@supabase/supabase-js` vía `cdn.jsdelivr.net`.
- **Playwright está instalado globalmente en esta máquina** (`npm install -g playwright`, navegador Chromium) exclusivamente como herramienta de testing. No es una dependencia del proyecto ni implica que la app necesite Node/npm para funcionar — los archivos `.html` se abren directamente en el navegador o se sirven estáticos; lo único que requiere Supabase es tener internet.
- **Paleta azul rey** en ambos archivos, con variantes distintas: `daphycel.html` usa fondo crema (`#f8f6f1`) con acento `#3d6fd6`; `daphycel-cliente.html` usa fondo beige cálido (`#f7f2e8`) con acento `#2540d6`. Mantener esta identidad visual al agregar features.

## Modelo de datos

El esquema relacional vive en Supabase (`supabase-schema.sql` + `supabase-schema-2.sql` + `supabase-schema-3.sql` + `supabase-schema-4.sql`) — ya no es un blob JSON único como en la primera versión con `localStorage` (documentada, ya superada, en `SPEC.md`/`FINDINGS.md`). Tablas: `products` (+ `product_reviews` en tabla aparte; columnas `image_url` y `barcode` opcionales), `customers`, `sales` (+ `sale_items`), `repairs` (doble identificador: `id` interno `EQ-###` para el panel, `order_no` público `OR-####` que consulta el cliente), `users` (sin acceso público directo), `counters` (incluye la clave `producto`, usada para el número de producto automático `DPC-########`), `caja` (+ `caja_cortes`), `settings`. El catálogo maestro son los 20 SKUs originales de la tienda (con `description`/`subcat`/reseñas) — su `sku` quedó fijo desde antes de que existiera el numerado automático; cualquier producto nuevo agregado desde el panel recibe su `sku` vía el contador `producto`. El checkout de la tienda genera una venta real (`method:'online'`, sin IVA, fuera de los cortes de caja) a través de la misma función `create_sale` que usa el panel. Cualquier cambio futuro al esquema debe ir en un nuevo archivo `.sql` versionado (no editar los existentes retroactivamente) y documentarse aquí antes de tocar código de la app.

**Campo `notifyEmail`** (tabla `settings`, clave `notify_email`): correo al que se avisa cuando se cambia la contraseña de cualquier cuenta. Solo se edita desde la vista Usuarios del panel (restringida al rol `dueno` en la UI). Sin servicio de correo propio, el aviso se envía abriendo un enlace `mailto:` con el mensaje redactado — no hay envío automático real ni se expone ninguna credencial de proveedor de email en el código.

## ⚠️ Esta base de datos es de producción real

Desde octubre 2026 la app está en uso real (sitio público — hospedado en GitHub Pages desde el
19 de octubre de 2026, antes estuvo en Netlify hasta que el despliegue se bloqueó por crédito agotado;
ver sección "Publicado en internet" de `README.md` para los links y el detalle del cambio —, cuentas reales
creadas por el dueño — ver `users_public` antes de asumir que `vendedor`/`admin` de la semilla siguen
existiendo, probablemente ya no). El repo es público en `github.com/pibemex10/daphycel` (requisito de
GitHub Pages gratis) y se publica solo vía GitHub Actions (`.github/workflows/pages.yml`), nunca a mano.
La base de Supabase del plan gratis se pausa sola tras 7 días sin actividad — hay un ping automático
(`.github/workflows/supabase-ping.yml`, cada 3 días) para evitarlo, pero si llegara a pausarse de nuevo
(por ejemplo si GitHub Actions se deshabilita o el ping falla silenciosamente por mucho tiempo), reactivarla
es manual desde el dashboard de Supabase — no hay forma de hacerlo por API con la clave `anon`.
**Nunca correr scripts de prueba/verificación directo contra la base de Supabase de este proyecto sin
limpiar después**, y nunca usar las credenciales de prueba viejas sin confirmar primero que la cuenta sigue
existiendo. Para pruebas: crear un usuario y/o producto temporal desechable (`create_user`/`insert`), probar,
y borrarlo con `delete_user`/`delete` al terminar — nunca editar ni borrar cuentas o productos reales sin que
el humano lo pida explícitamente. (Ya pasó una vez: la tabla `products` apareció vacía y sin la columna
`image_url` entre sesiones, aparentemente por una prueba de otra sesión que no limpió lo que tocó.)

## Reglas para cambios (Generator)

- **Cambios quirúrgicos.** Preferir ediciones puntuales sobre reescribir archivos completos. Mantener el estilo, nombres de variables/funciones y estructura ya existentes en cada archivo.
- **No romper lo que ya funciona.** Antes de modificar una sección compartida entre vistas (ej. `products`, `fmt`, `findProduct`), revisar todos los lugares que la usan dentro del mismo archivo.
- **Commits chicos y frecuentes**, uno por unidad de trabajo lógica, con mensajes descriptivos en español acordes al resto del proyecto.
- **Mantener el idioma español** en toda la UI, comentarios de cara a datos de ejemplo (nombres, productos) y mensajes al usuario.

## Cómo probar

Abrir el archivo `.html` correspondiente directamente en un navegador (con internet, para llegar a Supabase) — sigue sin requerir `npm install` ni servidor de desarrollo propio. Para pruebas automatizadas, Playwright con dos `browserContext` **independientes** (sin compartir cookies/storage) es la forma correcta de probar que los datos realmente se comparten entre "dispositivos" distintos, no solo entre pestañas — así quedó verificada esta migración (ver commits de octubre 2026). `window.DaphycelDB.read()` devuelve el estado completo desde Supabase para inspección en consola.
